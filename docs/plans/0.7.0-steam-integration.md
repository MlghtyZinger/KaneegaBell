## Outcome and scope

Installed Steam games join KB as a Steam platform and work in the existing desktop grid/list, Favorites, Recent, collections and TV layouts. Play opens the game through Steam. KB records its own observed sessions and returns focus when the actual game exits.

Steam only in this change. Other launchers, uninstalled ownership inventories, store browsing, account sign-in, installing/updating games, Steam achievements and publishing KB on Steam are outside this milestone. The old October decision to skip Steam is superseded by the November release schedule and the owner's current request. The AI Team remains removed; no external reviewing agents are required or invoked.

## Existing code and starting point

Use branch `codex/steam-integration`, worktree `C:/Emulator files/tmp/steam-integration`, based on current main `8703d75` (includes the post-0.6.0 audit fixes). Preserve the original checkout and unrelated sound-preview changes/drafts. No merge, public release, installed-copy changes or development-executable replacement is included in plan approval.

The app already has reusable scan progress/reporting, library rows, source settings, image caching, manual artwork choices, session events, controller navigation and native Windows APIs. Reuse these, with no new runtime dependency or general multi-launcher framework.

Critical differences: launcher/mod.rs currently spawns an emulator and immediately starts a timed session. launcher/process.rs tracks that child through a Job Object, and request_exit force-terminates its tree after a grace period. Neither behavior can be reused unchanged for Steam: Steam may already be running and spawn the real game later. Steam must never be placed in KB's emulator Job Object or force-terminated. Games use a platform/emulator foreign key today, and missing-source cleanup needs an explicit Steam association to distinguish an imported game from an orphaned ROM.

## User flow to approve

1. Settings > Library gets one Steam tile, using the existing Row/SetPanel and controller controls. Initially disconnected; Connect Steam explains the local files read, detects Steam's folder only after the player enables it, and offers Browse if detection fails. Scan library subsequently refreshes connected Steam libraries as well as ROM sources.
2. Steam appears as a normal platform once games have been imported. Existing filters, collections, artwork pickers and TV navigation work unchanged. Steam is presented as the launcher, without emulator/core/BIOS controls or ROM hashing.
3. Game details display Launch via Steam and, only when necessary, Choose game executable for session tracking. Choosing this file does not bypass Steam to launch it. The tracking file must be within that game's validated install directory.
4. Play opens a validated numeric App ID using the Windows protocol handler. During Steam startup, KB shows a waiting state; presentation Back skips the animation, as it does today. A distinct cancel-wait action returns to KB without closing Steam or an eventual game process. After about 60 seconds without a matching game process, report that the game could not be tracked and record no play time.
5. Exit combo/Close game sends WM_CLOSE only to the matched game windows. If the game remains open, show a clear notice and allow another polite close request or normal in-game exit. No forced termination.

Before visual implementation, provide a small preview of the Steam tile, waiting state and tracking-file fallback using the existing visual style, as the release schedule requires. This is an extension of existing controls, not a Settings or library redesign.

## Discovery and storage

- After permission, read only Steam install-location registry values, libraryfolders.vdf, appmanifest_<appid>.acf, the appinfo.vdf metadata cache if needed, and cached library artwork. Do not read loginusers, cookies, credentials, saves, screenshots, Workshop contents or installed game payloads beyond checking directories and executable paths.
- Parse the supported text KeyValues format with bounded input/depth and correct quoting, comments, escapes, casing and nested objects. Enumerate the primary and additional libraries, deduplicate canonical paths, validate numeric IDs and relative install directories, and confirm installed state plus an existing game directory. A directory alone is insufficient proof of installation.
- Manifest entries alone do not reliably distinguish games from tools or identify the actual game executable. Use local cached app metadata only for manifest-installed IDs to classify games and obtain Windows launch candidates. Guard the binary appinfo format version, record length and string-table bounds. Unknown/truncated cache formats must produce an actionable partial-result warning; never guess binary offsets or call private Steam endpoints. If classification is unavailable, offer explicit selection rather than silently importing unknown applications.
- Never persist product-access tokens or other incidental cache fields. No Steam SDK, client DLL loading, fake app identity or Steam Web API key is needed for the proposed local-file/protocol approach. Steam handles its existing account session and license checks.
- Add migration 029 for a small steam_games association: game_id FK, unique numeric app_id, library/install paths and optional confirmed tracking executable. Keep the stable game identity across rescans and moves so titles, favorites, artwork choices, collections and play history survive. Reuse games for displayed rows and an internal numeric-ID-derived Steam URI for its unique launch identity.
- Register a Steam platform and the minimum compatibility launcher record required by the existing schema; exclude it from emulator-template/core editors. Branch on the explicit Steam association at the launch/preview boundary, not on arbitrary URL text supplied by the UI.
- Reconcile successful library scans transactionally. An unavailable drive, malformed manifest, cancelled scan or unreadable cache is not evidence that its games were uninstalled. Only a completed authoritative scan marks missing entries; preserve history/manual choices, and update orphan pruning to respect Steam associations. All KB writes stay under its own data directory. Never write Steam's files.

## Launch and process tracking

- Valve documents steam://run/<AppId>. Use that URI, or an equivalent verified numeric rungameid URI, through ShellExecuteW in the existing windows crate. Do not assemble a shell command or append launch arguments from a manifest.
- Reserve a pending launch before opening Steam so double presses cannot create duplicate sessions. Steam bootstrap time is not play time, and game-started/running_since begin only when the actual game is identified.
- Match canonical full executable paths inside the validated install directory, with directory-boundary checks, not a process basename or loose string prefix. Use cached launch candidates or the user's explicit selection. Exclude Steam, third-party launcher/helper and anti-cheat processes. When a bootstrapper launches another game executable not identified by the cache, use the explicit tracking picker instead of choosing the largest executable or counting every process under the folder.
- Use limited Windows query/synchronization access and retained process handles/creation identity to avoid PID reuse. No hooks, injection, privileged service or game-memory reads. Do not attach to a pre-existing game as a newly started KB session without an explicit user action.
- Keep the owned-emulator tracker behavior for emulator games; add a concrete Steam tracking branch with a separate polite-only exit policy. Reuse current focus, manual overlay and low-resource game-running behavior only for confirmed game processes. Scan/wait work must be off the UI thread and stop when cancelled, timed out or finished; no Steam polling while KB is idle.
- Preserve failure handling and concurrency of the launch animation. A timed-out/cancelled pending launch must clear the same UI state and must not leave KB always-on-top or record phantom play time.

## Artwork and metadata

Reuse the existing source order and caching/manual-choice rules. Prefer Steam's already-cached library artwork when available; use the existing LaunchBox Windows mapping and optional metadata providers for gaps. Steam App ID lookup can improve the existing optional SteamGridDB client after verifying its current documented endpoint. Preserve user-picked artwork and metadata. No new mandatory key or store scraping; no promise that every game has a portrait cover or perfect title match.

## Service research and limits

- Valve's Steamworks documentation explicitly describes steam://run/<AppId> and notes Steam can launch a different executable from the initiating process: https://partner.steamgames.com/doc/api/steam_api . This supports protocol delegation, not a guarantee that the returned protocol process is the game.
- ISteamApps documents that GetAppInstallDir can return an install path even for an uninstalled app: https://partner.steamgames.com/doc/API/ISteamApps . Therefore directory lookup is not treated as installation proof; the plan does not embed Steamworks as a launcher-wide inventory API.
- libraryfolders/appmanifest handling is a local-client compatibility surface, not a published stable inventory API. Valve's own issue tracker shows both the library list and manifest scan in client logs: https://github.com/ValveSoftware/steam-for-linux/issues/13743 . Runtime results must tolerate disconnected libraries and future format changes.
- The author-maintained xPaw SteamAppInfo reference describes appinfo versions and the version-41 string table: https://github.com/xPaw/SteamAppInfo . This is reverse-engineered format documentation, not a Valve stability promise. Consult the implementation and its MIT license if adapting any code; retain attribution. Only implement verified versions with fixture tests.
- Local discovery and URI launching do not make Steam Web API requests, so there is no new API quota, key or purchase for KB. The Steam client can still perform its ordinary login, license, cloud-sync and update operations after the player presses Play; KB cannot guarantee an offline launch or suppress Steam's own behavior.
- Valve's subscriber agreement prohibits cheating, anti-cheat interference, process tampering and gameplay-stat automation: https://store.steampowered.com/subscriber_agreement/ . This plan uses user-initiated launches, normal OS process observation and KB-local session records. It does not make a legal or anti-cheat compatibility guarantee.
- Existing optional provider limits continue to apply. SteamGridDB uses the user's existing Bearer key, conservative sequential cached requests and 429 backoff; verify its API documentation before adding App ID lookup: https://www.steamgriddb.com/api/v2 . Do not invent a new quota or assume documentation guarantees unlimited requests.

## Implementation order and validation

1. Add the guarded local metadata readers and synthetic fixtures; test multiple libraries, stale/duplicate IDs, escaping, malformed/truncated input, unsupported cache versions, install-state changes, cancellation and path escape/reparse cases. Tests must not discover the real Steam installation as a side effect.
2. Add migration/import/reconciliation and test with temporary SQLite databases: repeated scan, moved library, changed title, actual uninstall versus offline drive, protected user data and ordinary ROM-scan/cleanup separation.
3. Add protocol dispatch and the pending/running session flow. Test process-candidate selection with synthetic snapshots, exact-path boundaries, helpers/anti-cheat, already-running processes, PID reuse, zero-match timeout and repeated polite close requests. Use controlled toy executables for Windows process observation only when authorized; never terminate or launch a real game during automated tests.
4. Extend the existing settings/detail/running states and metadata mappings after the compact preview is approved. Run TypeScript checks, JavaScript tests and relevant Rust tests, including emulator launch regressions and scan cancellation.
5. With separate permission to read Steam metadata, check against read-only copies from the owner's installation. Real game launch/exit tests remain manual and explicitly agreed. Inspect no other launchers.
6. Before a development build, confirm the owner is not playing and check for a running development KB executable. Do not overwrite a running exe. Performance gate is required because this affects startup/library/game-running flows, using a synthetic mixed 5,000-game library and Full versus Off animation comparison. The existing 0.6.0 gate failed; preserve its numbers and report new results honestly without resetting a baseline. A full release is a separate approval.
